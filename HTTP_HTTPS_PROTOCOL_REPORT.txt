3.1 Validation Process
-----------------------

Step 1: Certificate Retrieval
  Server sends:           - Server certificate

Step 2: Chain Validation
  Checks:                 - Certificate signature verification

  Security Model:         Public Key Infrastructure (PKI)
  Trust Root:             Certificate Authority (CA)

Step 3: Hostname Verification
  Server Certificate Has:
    - Subject Common Name (CN): CN=example.com
    - Subject Alternative Names (SAN): *.example.com, www.example.com

  Verification Process:
    1. Extract hostname from URL: example.com
    2. Check certificate CN field
    3. Check certificate SAN extension
    4. Support wildcard certificates (*.example.com)
    5. Case-insensitive matching
    6. Reject if no match

Step 4: Root CA Trust Verification
  Trust Chain:            Browser/OS/Python -> System CA Store -> Root CA
  Python Implementation:  certifi library provides Mozilla CA bundle
  System Implementation:  /etc/ssl/certs/ (Linux)
                          System Keychain (macOS)

3.3 Common Certificate Errors & Solutions
------------------------------------------

Error: CERTIFICATE_VERIFY_FAILED (self-signed certificate)
  Cause:              Certificate not signed by trusted CA
  Risk:               MAN-IN-THE-MIDDLE ATTACK LIKELY
  Solutions:          1. Obtain certificate from trusted CA
                      2. Add CA to trust store (development only)
                      3. Use certificate pinning if CA compromised

Error: CERTIFICATE_VERIFY_FAILED (hostname mismatch)
  Cause:              Certificate CN/SAN doesn't match hostname
  Risk:               CERTIFICATE SUBSTITUTION ATTACK
  Solutions:          1. Request correct hostname
                      2. Update certificate with correct CN/SAN
                      3. Configure certificate aliasing on server

Error: CERTIFICATE_VERIFY_FAILED (expired certificate)
  Cause:              Certificate passed expiration date
  Risk:               OUTDATED CERTIFICATE - SERVER MISCONFIGURATION
  Solutions:          1. Server administrator must renew certificate
                      2. Implement automated certificate renewal (ACME)
                      3. Monitor expiration dates

Error: CERTIFICATE_REVOKED
  Cause:              CA revoked certificate
  Risk:               COMPROMISED OR PROBLEMATIC CERTIFICATE
  Solutions:          1. Server must obtain new certificate
                      2. Implement certificate revocation checking (OCSP)
                      3. Distribute via CRL or OCSP stapling

Error: CERTIFICATE_VERIFY_FAILED (untrusted root)
  Cause:              Root CA not in trust store
  Risk:               CERTIFICATE FROM UNKNOWN/CUSTOM CA
  Solutions:          1. Add CA to system trust store
                      2. Use custom CA bundle for specific connections
                      3. Verify CA legitimacy before trusting

Certificate Pinning (for critical connections):
  import ssl
  import certifi
  import urllib.request
  import hashlib

  # Pin certificate's public key
  EXPECTED_PIN = "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="

  def verify_pin(cert_der):
      from cryptography import x509
      from cryptography.hazmat.primitives import hashes
      from cryptography.hazmat.primitives.serialization import Encoding
      import base64

      cert = x509.load_der_x509_certificate(cert_der)
      public_key = cert.public_key()
      spki = public_key.public_bytes(
          Encoding.DER,
          x509.SubjectPublicKeyInfo()
      )
      pin = "sha256/" + base64.b64encode(hashlib.sha256(spki).digest()).decode()

      if pin != EXPECTED_PIN:
          raise ssl.SSLError(f"Certificate pin mismatch: {pin}")

8. COMMON PITFALLS & HOW TO AVOID THEM
================================================================================

Pitfall #1: Disabling Certificate Verification for Testing
  Mistake:           context.verify_mode = ssl.CERT_NONE
  Why It's Bad:      Opens door to MITM attacks, hard to re-enable
  Solution:          - Keep verification enabled always
                     - For self-signed certs in dev, add to CA store
                     - Use proper certificates (Let's Encrypt free)
                     - Test ONCE, then enable verification

Pitfall #2: Ignoring SSL Exceptions
  Mistake:           try: ... except ssl.SSLError: pass
  Why It's Bad:      Certificate errors silently ignored, security bypassed
  Solution:          - Log SSL errors
                     - Alert on SSL errors
                     - Investigate root cause
                     - Fix before proceeding

Pitfall #3: Using HTTP for Authenticated Requests
  Mistake:           requests.get('http://api.example.com/user', auth=...)
  Why It's Bad:      Credentials transmitted in plain text
  Solution:          - Always use HTTPS for authenticated requests
                     - Check URL scheme is "https://"
                     - Enforce HTTPS in code

Pitfall #4: Hardcoding Certificates
  Mistake:           CERT_PATH = "/path/to/cert.pem"  # in code
  Why It's Bad:      Certificate rotation requires code change
  Solution:          - Load from configuration file
                     - Use environment variables
                     - Support certificate rotation without restart

Pitfall #5: Not Validating Certificate Expiration
  Mistake:           Ignore certificate validity dates
  Why It's Bad:      Connection fails when certificate expires
  Solution:          - Monitor certificate expiration
                     - Automate renewal (ACME)
                     - Alert 30+ days before expiration

Pitfall #6: Mixing HTTP and HTTPS
  Mistake:           Some requests HTTP, some HTTPS
  Why It's Bad:      Weakest link vulnerabilities
  Solution:          - Always use HTTPS
                     - Configure redirect HTTP -> HTTPS
                     - Block all HTTP requests in production

Pitfall #7: Not Testing Certificate Errors
  Mistake:           Code never tested with invalid certificates
