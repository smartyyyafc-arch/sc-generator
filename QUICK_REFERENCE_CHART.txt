DECISION MATRIX
================================================================================

SCENARIO 1: SIZE IS CRITICAL (Email, DNS, CLI limits)
  → USE BASE64
  Cost: Higher detection risk (common signature)
  Benefit: 45% smaller than alternatives
  Payload: 360-764 bytes range

SCENARIO 2: EVASION IS CRITICAL (Bypass AV/SIEM)
  → USE NESTED or POLYMORPH
  Cost: 50-80% larger payloads
  Benefit: Uncommon signatures, harder to analyze
  Payload: 569-872 bytes range

SCENARIO 3: BALANCED APPROACH (Most realistic)
  → USE BASE64 + VARIABLE OBFUSCATION
  Cost: Some detection risk
  Benefit: Minimal payloads + variable naming evasion
  Payload: 360-764 bytes range
  Combine with: Random variable names, function wrappers

SCENARIO 4: MAXIMUM OBFUSCATION (Detection lab evasion)
  → USE NESTED (3-layer: Base64→Hex→Reverse)
  Cost: 2.7x overhead (highest)
  Benefit: Extremely rare signature patterns
  Payload: 464-1272 bytes range
  Note: Use only if size is not a constraint

SCENARIO 5: SPEED MATTERS (Real-time encoding)
  → USE HEX (0.003ms - fastest)
  Cost: 50% larger than Base64
  Benefit: Minimal CPU usage
  Payload: 387-989 bytes range
  Note: Negligible (all methods <0.02ms total)

================================================================================
PLATFORM-SPECIFIC NOTES
================================================================================

VBS DELIVERY:
  • Decoder adds ~120 bytes boilerplate
  • Base64 + MSXML is most efficient
  • Payload bottleneck: VBS decoder complexity
  • Best: Base64 (360-764 bytes)
  • Worst: Array (556-1492 bytes)

POWERSHELL DELIVERY:
  • FromBase64String is native (no external tools)
  • All methods roughly equivalent after decoding
  • Benefi from built-in cmdlets
  • Best: Base64 (uses native decoding)

BASH DELIVERY:
  • External tools add overhead (base64, xxd, od)
  • Encoding method matters less than platform
  • Pipeline complexity is the constraint
  • Best: Any (all similar 400-700 bytes)

PYTHON DELIVERY:
  • Most flexible implementation
  • Decoder code varies by method
  • Can optimize decoder for any method
  • Best: Base64 (smallest decoder)

OVERHEAD RATIO ANALYSIS
================================================================================

OVERHEAD RATIO = (Encoded Size / Original Size) × 100

Base64:    1.33x (33% expansion)     - Most efficient
Hex:       2.00x (100% expansion)    - Mathematical minimum for hex
XOR:       2.00x (100% expansion)    - Same as hex (stored as hex)
Array:     2.05x (105% expansion)    - Chunking overhead
Polymorph: 1.76x (76% expansion)     - Average of selected methods
Nested:    2.70x (170% expansion)    - Multiple encoding layers

Key insight: Base64 is mathematically optimal (4:3 compression)

FINAL RECOMMENDATION
================================================================================

FOR 95% OF CASES: Use Base64
  ✓ Lowest overhead (133.9%)
  ✓ Smallest payloads (500 bytes avg)
  ✓ Fast encoding (0.009ms)
  ✓ Universal platform support
  ✓ Easy decoder implementation
  ✓ Negligible performance cost

  Mitigate detection by adding:
  • Random variable names (prefix: v_, func_, etc)
  • Function wrappers with obfuscation
  • Environment variable storage
  • Dead code blocks

FOR SIZE-CONSTRAINED: Use Base64 (even better than 95% case)
  • Email attachments
  • DNS exfiltration (255 byte DNS name limit)
  • Command-line argument limits
  • Network bandwidth constraints

FOR EVASION-FOCUSED: Use Nested + Variable Obfuscation
  • Trade 50% size increase for detection evasion
  • Uncommon signature patterns
  • Complex multi-layer decoding logic
  • Use only when detection risk > size constraints

FOR SPEED-CRITICAL: Use Hex (0.005ms)
  • Fastest encoding available
  • Consistent 2.0x overhead
  • Only relevant for bulk/streaming scenarios
  • Real-world impact: negligible (<0.02ms)
