NAMING STRATEGIES IMPLEMENTED
================================================================================

1. SYSTEM_LEGACY
   - Legacy Windows system variable names (TEMP, WINDIR, etc.)
   - Legitimacy: VERY HIGH
   - Best For: Windows enterprise environments
   - Example: TEMP_PATH_001, SYSTEMROOT_CACHE_002

2. COMMON_TOOLS
   - Popular development tool prefixes (NODE_, PYTHON_, GIT_, NPM_)
   - Legitimacy: VERY HIGH
   - Best For: Developer machines, CI/CD pipelines
   - Example: NODE_PATH_001, PYTHON_HOME_002

3. BUILD_SYSTEM
   - Build tool prefixes (CMAKE_, GRADLE_, MAVEN_, MAKE_, BAZEL_)
   - Legitimacy: HIGH
   - Best For: Build environments, compilation systems
   - Example: CMAKE_BUILD_001, GRADLE_CONFIG_002

4. DEVELOPMENT
   - Development/test prefixes (DEBUG_, DEV_, TEST_, SANDBOX_)
   - Legitimacy: HIGH
   - Best For: Local development, testing systems
   - Example: DEBUG_MODE_001, TEST_DATA_002

5. FRAMEWORK
   - Web framework prefixes (DJANGO_, FLASK_, REACT_, EXPRESS_)
   - Legitimacy: HIGH
   - Best For: Web application deployments
   - Example: DJANGO_SETTINGS_001, FLASK_ENV_002

6. CONTAINER
   - Container/VM prefixes (DOCKER_, K8S_, KUBERNETES_, PODMAN_)
   - Legitimacy: HIGH
   - Best For: Docker/Kubernetes deployments
   - Example: DOCKER_HOST_001, K8S_NAMESPACE_002

7. CI_CD
   - CI/CD pipeline prefixes (CI_, GITHUB_, GITLAB_, JENKINS_)
   - Legitimacy: HIGH
   - Best For: CI/CD pipelines and automation
   - Example: CI_COMMIT_001, GITHUB_TOKEN_002

8. CLOUD
   - Cloud provider prefixes (AWS_, AZURE_, GCP_, HEROKU_)
   - Legitimacy: HIGH
   - Best For: Cloud provider deployments
   - Example: AWS_ACCESS_KEY_001, AZURE_TENANT_002

9. RUNTIME
   - Language runtime prefixes (JAVA_, RUST_, GO_, PYTHONPATH)
   - Legitimacy: HIGH
   - Best For: Language-specific environments
   - Example: JAVA_HOME_001, RUST_FLAGS_002

10. HASH_BASED
    - Cryptographic hash-based names (deterministic)
    - Legitimacy: MEDIUM
    - Best For: Reproducible, covert scenarios
    - Example: NODE_A3F2C8D1, PYTHON_5B9E7C2F

11. RANDOM_ALPHA
    - Pure random alphanumeric strings
    - Legitimacy: LOW
    - Best For: High randomization scenarios
    - Example: XKQM7F9P2J, B4WL8N3R9T

12. MIXED_CASE
    - Random case variation (typo-like appearance)
    - Legitimacy: MEDIUM
    - Best For: Mimicking human typos
    - Example: NoDeJS_PaTh_001, PyThOn_HoMe_002

13. ACRONYM
    - Pronounceable-ish acronyms (consonant-vowel alternation)
    - Legitimacy: MEDIUM
    - Best For: Enterprise custom naming
    - Example: MORIDA_PATH_001, BELOTA_CONFIG_002

================================================================================
STRATEGY SELECTION GUIDE
================================================================================

BY ENVIRONMENT TYPE:
  Windows Enterprise      → SYSTEM_LEGACY (+ BUILD_SYSTEM, COMMON_TOOLS)
  Developer Machine      → COMMON_TOOLS (+ DEVELOPMENT, FRAMEWORK)
  Build System           → BUILD_SYSTEM (+ CI_CD, COMMON_TOOLS)
  CI/CD Pipeline         → CI_CD (+ BUILD_SYSTEM, CLOUD)
  Kubernetes             → CONTAINER (+ CLOUD, RUNTIME)
  AWS/Cloud              → CLOUD (+ CI_CD, CONTAINER)
  Web Application        → FRAMEWORK (+ COMMON_TOOLS, DEVELOPMENT)
  Local Development      → DEVELOPMENT (+ COMMON_TOOLS, FRAMEWORK)
  Covert/Stealthy        → HASH_BASED (+ MIXED_CASE, ACRONYM)

BY LEGITIMACY:
  Highest   → SYSTEM_LEGACY (uses real Windows system vars)
  Very High → COMMON_TOOLS (used by millions of developers)
  High      → BUILD_SYSTEM, DEVELOPMENT, FRAMEWORK, CONTAINER, CI_CD, CLOUD
  Medium    → HASH_BASED, MIXED_CASE, ACRONYM (harder to reverse-engineer)
  Low       → RANDOM_ALPHA (pure random, looks suspicious)

================================================================================
CONFIGURATION OPTIONS
================================================================================

NamingStrategyConfig Parameters:
  - primary_strategy: NamingStrategy (main strategy to use)
  - fallback_strategies: List[NamingStrategy] (backup strategies)
  - add_version_suffix: bool (add suffix to names) [default: True]
  - add_timestamp: bool (add timestamp component) [default: False]
  - randomize_case: bool (randomize letter case) [default: True]
  - min_name_length: int (minimum length, default: 8)
  - max_name_length: int (maximum length, default: 32)
  - use_underscores: bool (allow underscores) [default: True]
  - use_numbers: bool (allow numbers) [default: True]
  - chunk_numbering: str ("sequential", "hex", "random") [default: "sequential"]
  - separator: str (separator character) [default: "_"]
  - seed: Optional[int] (random seed for reproducibility)

EnhancedEnvVarConfig Parameters:
  - scope: EnvVarScope (PROCESS, USER, SYSTEM) [default: PROCESS]
  - encoding: EnvVarEncoding (RAW, BASE64, HEX, etc.) [default: BASE64]
  - chunk_size: int (bytes per chunk) [default: 255]
  - prefix: str (variable prefix) [default: "SC_"]
  - naming_strategy: NamingStrategy [default: COMMON_TOOLS]
  - fallback_naming_strategies: List[NamingStrategy]
  - randomize_case: bool [default: True]
  - chunk_numbering: str [default: "sequential"]
  - use_strategy_rotation: bool (rotate through strategies) [default: False]
  - naming_seed: Optional[int]
  - track_metadata: bool (store metadata) [default: True]
  - include_checksum: bool (include SHA256) [default: True]

KEY INSIGHT
================================================================================

The naming strategy succeeds by making variables look LEGITIMATE rather than
RANDOM. This is achieved by:

1. Using REAL prefixes from actual tools and platforms
2. Combining with COMMON suffixes from configuration names
3. Following PLATFORM CONVENTIONS (UPPER_CASE for env vars)
4. Supporting ENVIRONMENT-AWARE selection
5. Allowing ROTATION to prevent pattern detection
6. Including METADATA strategies for edge cases

The best variable name is one that looks exactly like a variable that SHOULD
be there in that environment. This guide provides 13 different ways to achieve
this level of legitimacy across diverse deployment contexts.
