================================================================================
EFFICIENCY RATIO EXPLAINED
================================================================================

Efficiency = Hex Data Length / Total VBS Code Length

Higher ratio = more "useful" data in output, less "wasted" overhead code

Examples (561-byte payload):

8-byte chunks (71 chunks):
  Hex data: 1,122 bytes
  Total code: 3,024 bytes
  Efficiency: 1,122 / 3,024 = 0.3710 (37% useful)
  Overhead code: 1,902 bytes (63%)

16-byte chunks (36 chunks):
  Hex data: 1,122 bytes
  Total code: 2,254 bytes
  Efficiency: 1,122 / 2,254 = 0.4978 (50% useful)
  Overhead code: 1,132 bytes (50%)

32-byte chunks (18 chunks):
  Hex data: 1,122 bytes
  Total code: 1,858 bytes
  Efficiency: 1,122 / 1,858 = 0.6039 (60% useful) ← BEST
  Overhead code: 736 bytes (40%)

Key insight: Fewer chunks = less overhead code per hex data unit


================================================================================
GENERATION TIME PERFORMANCE
================================================================================

Generation is very fast overall (all <1ms), but relative performance:

Average Generation Time:
  8-byte:  0.0282 ms  (Baseline relative)
  16-byte: 0.0526 ms  (Baseline for comparison)
  32-byte: 0.0118 ms  (77.6% faster than 16-byte!)

Why 32-byte is faster:
  1. Fewer chunks to loop through (5.6 vs 10.6)
  2. Fewer array assignments to generate (18 vs 36 for 561B payload)
  3. Less Python string concatenation overhead
  4. Simpler VBS code structure

Practical impact: ~0.04ms saved per typical payload (negligible for users)
But better for high-throughput payload generation scenarios


================================================================================
DETECTION EVASION ANALYSIS
================================================================================

Advantage: 32-BYTE CHUNKS

Why smaller code is better for evasion:

Signature Detection Factors:
  1. Code footprint size
     - Smaller code = smaller target for static analysis
     - Less data to match against signatures
     → 32-byte wins

  2. Pattern repetition
     - More chunks = more repeated patterns
     - Patterns: Dim, array assignment, For loop, etc.
     - 8-byte: 71 repetitions (highly detectable)
     - 32-byte: 18 repetitions (much stealthier)
     → 32-byte wins

  3. Array element diversity
     - 8-byte: might seem more diverse
     - But: repetitive structure is more obvious
     → 32-byte's fewer elements are actually less suspicious

  4. Overall footprint
     - VBS code analyzer sees smaller total size
     - Less obvious obfuscation attempt
     → 32-byte wins

Verdict: 32-byte chunks superior for detection evasion

IMPLEMENTATION COMPLEXITY
================================================================================

Change Required: Extremely Simple

Current code (line 145):
  chunks = [text[i : i + 16] for i in range(0, len(text), 16)]

New code:
  chunks = [text[i : i + 32] for i in range(0, len(text), 32)]

Or with configurability:
  def create_array_concatenation_decoder(self, text: str, chunk_size: int = 32):
      chunks = [text[i : i + chunk_size] for i in range(0, len(text), chunk_size)]

Complexity: 1 line change (or parameter addition)
Risk: Zero (fully backward compatible)
Testing: Minimal (existing tests just need 1 constant update)
